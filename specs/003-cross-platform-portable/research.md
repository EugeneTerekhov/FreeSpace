# Research: FreeSpace 2.0 — кроссплатформенность и portable-поставка

**Feature**: `003-cross-platform-portable` | **Date**: 2026-11-19

## 1. Кроссплатформенная архитектура: трейты vs `cfg`

**Решение**: узкие object-safe трейты по возможностям + единая точка сборки `platform()`;
`cfg` только в composition root, target-зависимостях и Windows-only модулях.

**Обоснование**:

- Верхние слои (`ops`, `app`, CLI, Tauri) не должны знать о платформе; это единственный способ
  сохранить единый код и не размазать `cfg` по сотням мест.
- Трейты делают возможным подменяемый бэкенд в тестах и контрактные тесты для двух реализаций.
- Разные возможности (`trash`, `shred`, `acl`) естественно ложатся на разные трейты; один
  «god trait» усложнил бы поддержку и тестирование.
- `Capabilities` позволяет GUI/CLI честно скрывать недоступное и возвращать `E_UNSUPPORTED`.

**Отклонено**:

- `cfg` в каждом модуле — быстро для первого порта, но далее невозможно поддерживать.
- Один трейт `Platform` на 40 методов — нарушает разделение ответственности, тяжело тестировать.
- Динамическая регистрация плагинов — избыточна для двух ОС.

## 2. Сканирование Linux: только walk

**Решение**: на Linux нет MFT/USN; используется `jwalk`-обход, метод явно показывается в UI и
JSON.

**Обоснование**:

- MFT — проприетарная структура NTFS; на ext4/btrfs/xfs её нет.
- USN-журнал — Windows-only.
- Обход дерева уже реализован и покрыт тестами; он же используется на Windows для не-NTFS.
- Бюджет 8 ТБ / 60 с к Linux неприменим; отдельный бюджет — 1 млн файлов ≤ 5 мин на локальном
  SSD, память ≤ 4 ГБ на 10 млн узлов.

**Отклонено**:

- Чтение сырых inode-таблиц ext4/btrfs — огромная сложность и риск, вне 2.0.
- Эмуляция MFT через `find`/`du` — медленно и не даёт нужной модели.

## 3. Linux: объём и занятое место

**Решение**:

- список томов — `/proc/self/mounts` с раскодированием `\040`, `\011`, `\134`;
- `statvfs` через `rustix::fs::statvfs` для total/free/block size;
- allocated size — `std::os::unix::fs::MetadataExt::blocks() * 512`;
- sparse-файлы учитываются естественно через `blocks`;
- cluster size — `statvfs.f_frsize` (для отчёта, не для точного учёта).

**Обоснование**: это стандартные, дешёвые и точные для Linux источники; `st_blocks` уже отражает
реальный расход, включая sparse и copy-on-write.

**Отклонено**:

- `sysinfo` — тяжёлая зависимость ради того, что даёт `statvfs`.
- `du`/`df` через внешние процессы — не офлайн-библиотечно и медленно.

## 4. XDG trash

**Решение**: собственная реализация freedesktop trash в `unix/trash.rs`; `percent-encoding` для
`.trashinfo`.

**Поведение**:

- домашняя корзина: `$XDG_DATA_HOME/Trash` (по умолчанию `~/.local/share/Trash`);
- для других томов: `$topdir/.Trash/$uid` (если каталог уже есть и безопасен) или
  `$topdir/.Trash-$uid`;
- файлы: `files/<name>` с разрешением коллизий; метаданные: `info/<name>.trashinfo`
  (`Path=`, `DeletionDate=` в ISO 8601);
- `Path` — абсолютный путь, percent-encoded по RFC 2396;
- ошибки: нет прав, read-only том, сетевой том, отсутствующий `$topdir` → `Error::Unsupported`
  или `Error::Io`, **без** молчаливого permanent;
- restore — системными средствами (файловый менеджер), приложение restore не делает.

**Обоснование**: карантин на Linux дублировал бы корзину и занимал место на очищаемом томе;
XDG — стандарт, который понимают файловые менеджеры.

**Отклонено**:

- Крейт `trash`: скрывает детали, тянет зависимости и не даёт нужного контроля над ошибками
  per-volume; при этом Windows-реализация остаётся нативной.
- Всегда permanent: опасно и противоречит принципу I.

## 5. Метаданные Linux: атрибуты, владельцы, ACL, ADS

**Решение**:

- `attributes` — `mode`/`FileAttributes`-совместимое представление только для чтения; запись
  атрибутов Windows (`Read-only`, `Hidden`, `System`, `Archive`) недоступна (`Capabilities.attrs
  = false`);
- владелец — uid/gid; имя пользователя ищется в `/etc/passwd` (небольшой парсер), иначе
  выводится числовой uid;
- ACL — `E_UNSUPPORTED` (POSIX ACL — отдельная фича, вне 2.0);
- ADS — пустой список/`E_UNSUPPORTED`;
- ссылки — `symlink_metadata`, точки монтирования — по таблице монтирования.

**Обоснование**: не эмулировать NTFS-семантику там, где её нет; при этом владельцы нужны для
отчётов.

**Отклонено**:

- `nix`/`uzers` — лишние зависимости ради `/etc/passwd`.
- Полная поддержка POSIX ACL в 2.0 — расширение области.

## 6. Мониторинг записи на Linux

**Решение**: `MonitorBackend` на `/proc/<pid>/io` (read_bytes/write_bytes) и перечислении
`/proc`; ETW недоступен, используется polling-fallback, уже существующий в
`freespace-scan::monitor_fallback`.

**Обоснование**: работает без root и без сторонних демонов; тот же интерфейс, что на Windows.

**Отклонено**:

- `inotify` — не даёт per-process I/O и не отвечает на вопрос «кто пишет».
- `fanotify` — требует привилегий и сложнее в поддержке.

## 7. Unlock, elevation, context menu, shred на Linux

**Решение**:

- `unlock` — `Unsupported` (нет Restart Manager; реализация через `/proc/*/fd` вне 2.0);
- `elevation` — `geteuid() == 0` для отображения состояния; перезапуск с повышением не
  реализуется (пользователь запускает `sudo` сам);
- `context_menu` — `Unsupported` (portable-сборка и на Windows его не регистрирует);
- `shred` — `Unsupported`; на Windows остаётся CLI-only;
- `trim` — `Unsupported`; нужен только шредеру.

**Обоснование**: не обещать функции, которые нельзя выполнить надёжно; уменьшает объём порта и
риск ложных гарантий.

## 8. Пути, регистр, длинные пути

**Решение**:

- Windows `PathPolicy` — существующая verbatim-логика, `MAX_PATH_CHARS = 32_000`;
- Linux `PathPolicy` — `std::path`, `PATH_MAX = 4096` (константа с пояснением; `pathconf` не
  используется), `volume_root` — ближайшая точка монтирования;
- `equivalent_key` — Windows: lower-case; Linux: точное значение (регистрозависимость);
- `rename_plan` использует `equivalent_key` вместо `to_lowercase`;
- проверка длины — до операции, с понятной ошибкой.

**Обоснование**: регистрозависимость — источник ложных конфликтов; `PATH_MAX` нельзя игнорировать.

**Отклонено**:

- Полагаться на `LongPathsEnabled` — уже запрещено конституцией/AGENTS.
- Приводить Linux-пути к Windows-виду — ломает семантику.

## 9. Защищённые пути

**Решение**:

- Windows — существующий список (`SystemRoot`, `Program Files`, `ProgramData`, …);
- Linux — `/`, `/bin`, `/boot`, `/dev`, `/etc`, `/lib`, `/lib64`, `/proc`, `/root`, `/sbin`,
  `/sys`, `/usr`, `/var` (без `/home`, `/tmp`, `/opt`, `/srv`);
- операция над protected path требует дополнительного подтверждения; набор — платформенный
  трейт.

**Обоснование**: защита системных каталогов — часть принципа I; список должен быть осмысленным,
а не копией Windows.

## 10. Portable-формат Linux: tar.gz, не AppImage

**Решение**: tar.gz с `freespace-gui`, `freespace`, документацией и `data/`.

**Обоснование**:

- `settings.rs` хранит данные в `data` рядом с exe; AppImage монтирует squashfs read-only,
  запись рядом с бинарником невозможна;
- tar.gz — прямой аналог Windows ZIP, без установки;
- WebKitGTK/GTK3 остаются системными зависимостями; это документируется.

**Отклонено**:

- AppImage — требует менять модель хранения или писать в `$OWD`, что ломает переносимость.
- Flatpak/Snap/deb — установка, противоречит portable-only.

## 11. Релизный процесс

**Решение**: `workflow_dispatch` с обязательным `tag`; matrix; финальный job создаёт/обновляет
draft через `softprops/action-gh-release@v2`; публикация вручную.

**Обоснование**:

- «Не на каждый тег нужен релиз» — ручной запуск решает это лучше фильтра по тегам;
- draft позволяет проверить артефакты до публикации;
- проверка `tag == version` предотвращает релиз с неверной версией;
- matrix + финальный job исключает частичный релиз.

**Отклонено**:

- Автозапуск на `push: tags` — создаёт релизы для служебных тегов.
- `release: published` — артефакты появлялись бы после публикации, что хуже для проверки.
- Сборка только на Windows с кросс-компиляцией Linux — хрупко и не поддерживается Tauri.

## 12. Версионирование

**Решение**: `Cargo.toml` — источник истины; `scripts/version.mjs set|check`; portable-скрипты
читают версию из Cargo.toml; workflow проверяет тег.

**Обоснование**: сейчас версия продублирована в 7 местах (Cargo.toml, tauri.conf.json,
package.json/lock, README, user guides, portable.ps1, mockTransport). Скрипт и CI-проверка
устраняют рассинхрон.

**Отклонено**:

- Ручное обновление — уже приводило к расхождениям.
- Хранение версии только в `package.json` — Rust-сборка всё равно берёт Cargo.toml.

## 13. Зависимости

| Зависимость | Область | Обоснование |
|---|---|---|
| `rustix` (`fs`, `process`) | `cfg(unix)` | Безопасные обёртки `statvfs`, `geteuid`, `flock`, `fsync`; без `unsafe` в unix-бэкенде |
| `percent-encoding` | `cfg(unix)` | Корректный `.trashinfo` по freedesktop |
| `windows`, `winreg`, `ferrisetw` | `cfg(windows)` | Переносятся в target-зависимости; других изменений нет |

Новые зависимости не добавляются в runtime-поставку сверх уже существующих; обе лицензионно
совместимы (MIT/Apache-2.0).
