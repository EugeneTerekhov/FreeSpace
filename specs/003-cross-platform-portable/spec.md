# Feature Specification: FreeSpace 2.0 — Linux portable, упрощение очистки и ручные релизы

**Feature Branch**: `003-cross-platform-portable`

**Created**: 2026-11-19

**Status**: Draft

**Input**: Пользовательское описание: «Linux portable и Windows portable, только portable-сборки без
инсталляторов; quarantine убрать полностью; shred оставить только в Windows CLI; удаление — Recycle
Bin / XDG trash и permanent; экраны «Шредер» и «Файловые операции» убрать, контекстный rename
оставить, permissions/attrs — только CLI; публикация релиза вручную из выбранного тега; сборки без
подписи; разные платформенные реализации — за общим интерфейсом».

## Обзор

FreeSpace 2.0 превращает продукт из Windows-only утилиты в **кроссплатформенное portable-приложение**
для Windows 10/11 x64 и Linux x86_64. Одновременно продукт упрощается: удаляется карантин, шредер
остаётся только в Windows CLI, графический интерфейс сокращается с 11 до 9 экранов, а поставка
переходит на два portable-архива без установщиков. Публикация релиза выполняется вручную из
выбранного тега, поэтому не каждый тег становится релизом.

Платформенные различия изолируются в `freespace-platform` за общим набором трейтов; верхние слои
(`freespace-ops`, `freespace-app`, CLI, Tauri) работают через `Capabilities` и не содержат
платформенных ветвлений.

## Clarifications

### Session 2026-11-19

- Q: Какие платформы входят в 2.0? → A: Windows 10 21H2+/11 x64 и Linux x86_64 (portable).
- Q: Какие форматы поставки? → A: только portable: Windows ZIP, Linux tar.gz. Инсталляторы
  (NSIS и любые другие) не выпускаются.
- Q: Что делать с карантином? → A: удалить полностью — код, БД, настройки, UI, CLI и документацию.
- Q: Что делать со шредером? → A: убрать из GUI; оставить только в Windows CLI; на других
  платформах возвращать `E_UNSUPPORTED`.
- Q: Какие режимы удаления остаются? → A: системная корзина (Recycle Bin / XDG trash) и permanent.
- Q: Что делать с экранами «Шредер» и «Файловые операции»? → A: убрать из GUI; CLI-команды
  `shred`, `rename`, `acl`, `attrs` сохранить. Контекстный rename в дереве остаётся.
- Q: Как публиковать релизы? → A: вручную, по выбранному тегу, через запуск workflow; черновик
  релиза публикуется человеком. Не каждый тег создаёт релиз.
- Q: Подпись сборок? → A: нет сертификата; сборки неподписанные.
- Q: Linux portable: AppImage или tar.gz? → A: tar.gz. Приложение хранит `data` рядом с
  исполняемым файлом, а AppImage монтирует образ только для чтения.
- Q: Где заканчивается кроссплатформенность? → A: macOS, ARM и мобильные платформы вне области 2.0.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Linux portable: анализ и очистка без установки (Priority: P1)

Пользователь Linux скачивает `freespace-portable-<version>-linux-x86_64.tar.gz`, распаковывает в
любой каталог и запускает GUI или CLI. Приложение анализирует выбранный каталог или точку
монтирования, показывает дерево, дубликаты и отчёты, а удаление выполняет в системную корзину
(XDG trash) или безвозвратно — после предпросмотра и подтверждения. Данные приложения лежат в
каталоге `data` рядом с исполняемыми файлами; установка не требуется.

**Why this priority**: это основная новая ценность 2.0 — продукт перестаёт быть Windows-only.

**Independent Test**: на чистой Ubuntu 22.04 распаковать архив, запустить `freespace scan` по
временному дереву и GUI, выполнить удаление во временную XDG-корзину и permanent; проверить
журнал и отсутствие записей вне каталога приложения.

**Acceptance Scenarios**:

1. **Given** распакованный Linux-архив, **When** пользователь запускает `freespace --json
   capabilities`, **Then** вывод содержит платформу `linux`, доступные возможности `trash`,
   `permanent`, `walk`, `rename` и недоступные `mft`, `usn`, `shred`, `acl`, `attrs`, `unlock`,
   `context_menu`.
2. **Given** каталог с файлами, **When** пользователь запускает сканирование, **Then** метод
   сканирования явно указан как обход дерева, прогресс отображается постепенно, а отчёт
   соответствует содержимому.
3. **Given** выбранный файл, **When** пользователь подтверждает удаление в корзину, **Then** файл
   исчезает из исходного каталога, появляется в XDG-корзине, а операция записывается в журнал.
4. **Given** выбранный файл, **When** пользователь выбирает permanent и подтверждает, **Then**
   файл удаляется безвозвратно, а интерфейс показывает предупреждение о необратимости.
5. **Given** том, на котором XDG-корзина недоступна, **When** пользователь выбирает удаление в
   корзину, **Then** приложение показывает ошибку и предлагает permanent с отдельным
   подтверждением; молчаливого перехода в permanent не происходит.
6. **Given** распакованный архив, **When** приложение запускается без установленных библиотек
   WebKitGTK/GTK3, **Then** сообщение об ошибке называет отсутствующие пакеты и не оставляет
   частично созданных данных.

### User Story 2 — Windows portable без инсталлятора (Priority: P1)

Пользователь Windows скачивает `freespace-portable-<version>-windows-x64.zip`, распаковывает и
запускает GUI или CLI. Установщик NSIS больше не выпускается; всё, что нужно, лежит в архиве.
Приложение по-прежнему использует MFT/USN, Recycle Bin и контекстный rename, но без карантина,
без экрана шредера и без экрана «Файловые операции».

**Why this priority**: сохранение существующей аудитории и паритета Windows-функций при смене
формата поставки.

**Independent Test**: на чистой Windows 10 21H2 и Windows 11 x64 распаковать ZIP, просканировать
тестовый VHD, удалить файл в Корзину и permanent, проверить журнал, отсутствие записей в реестре
и отсутствие установщика среди артефактов.

**Acceptance Scenarios**:

1. **Given** распакованный ZIP, **When** пользователь запускает GUI, **Then** приложение работает
   без установки и хранит данные в `data` рядом с `.exe`.
2. **Given** NTFS-том, **When** пользователь сканирует его, **Then** применяется MFT-сканирование,
   а повторное сканирование поддерживает инкрементальное обновление через USN.
3. **Given** файл, **When** пользователь удаляет его в Корзину, **Then** файл восстанавливается
   штатными средствами Windows, а журнал FreeSpace содержит запись без возможности
   внутриприложенческого restore.
4. **Given** распакованный ZIP, **When** пользователь проверяет контекстное меню дерева, **Then**
   доступны rename, открытие в Проводнике, копирование пути и удаление, но нет пунктов,
   ведущих к шредеру или карантину.

### User Story 3 — Упрощённая и безопасная модель удаления (Priority: P2)

Пользователь выполняет удаление только двумя способами: в системную корзину или безвозвратно.
Карантина приложения больше нет: он не занимает место на очищаемом диске, не требует срока
хранения и не создаёт второй механизм восстановления. Все операции по-прежнему проходят
предпросмотр, подтверждение и журналирование.

**Why this priority**: упрощает продукт и убирает функцию, которая дублировала системную корзину
и тратила место.

**Independent Test**: проверить, что в CLI нет режима `quarantine`, в GUI нет выбора карантина,
в настройках нет срока хранения, в журнале нет restore, а старые записи журнала остаются
читаемыми.

**Acceptance Scenarios**:

1. **Given** запрос `freespace delete --mode quarantine`, **When** команда выполняется, **Then**
   возвращается ошибка валидации со списком допустимых режимов `recycle` и `permanent`.
2. **Given** диалог удаления, **When** пользователь открывает выбор режима, **Then** доступны
   только «Корзина» и «Удалить безвозвратно».
3. **Given** существующая база с записями карантина, **When** приложение обновляется до 2.0,
   **Then** миграция схемы проходит без потери журнала, старые записи отображаются как аудит,
   а каталог `data/quarantine` не удаляется автоматически.
4. **Given** журнал с записью удаления, **When** пользователь открывает её, **Then** нет кнопки
   restore; для записей rename доступна отмена переименования.

### User Story 4 — Меньше экранов, больше ясности (Priority: P2)

Пользователь видит 9 экранов вместо 11. «Шредер» и «Файловые операции» убраны из навигации.
Переименование остаётся в контекстном меню дерева; пакетное переименование, права, атрибуты и
шредер доступны из CLI.

**Why this priority**: экраны дублировали CLI и почти не использовались, а шредер на SSD/CoW
создавал ложное чувство безопасности.

**Independent Test**: открыть приложение, перебрать все пункты сайдбара, проверить отсутствие
`shred`/`fileops`, доступность контекстного rename и наличие CLI-команд.

**Acceptance Scenarios**:

1. **Given** запущенное приложение, **When** пользователь открывает сайдбар, **Then** в нём
   ровно 9 экранов: Обзор, Дерево, Анализ, Дубликаты, Очистка, Журнал, Мониторинг, Инспекция,
   Настройки.
2. **Given** сохранённый экран `fileops` или `shred` из версии 1.x, **When** приложение
   запускается, **Then** открывается ближайший живой экран (`tree` или `journal`) без ошибки.
3. **Given** контекстное меню строки дерева, **When** пользователь выбирает rename, **Then**
   открывается диалог переименования с предпросмотром и подтверждением.
4. **Given** CLI, **When** пользователь запрашивает `shred`, `rename`, `acl` или `attrs`,
   **Then** команда доступна, а на неподдерживаемой платформе возвращает `E_UNSUPPORTED`.

### User Story 5 — Ручной релиз из выбранного тега (Priority: P2)

Сопровождающий создаёт тег `vX.Y.Z`, затем вручную запускает workflow релиза и указывает этот тег.
Workflow собирает Windows ZIP и Linux tar.gz, считает контрольные суммы и создаёт черновик
релиза. Сопровождающий проверяет артефакты и публикует релиз вручную. Теги, для которых релиз не
нужен, ничего не запускают.

**Why this priority**: текущий репозиторий не имеет release-workflow, а версии не попадают в
релизы; публикация на каждый тег нежелательна.

**Independent Test**: создать тег на тестовой ветке, запустить workflow с этим тегом, проверить
черновик релиза с двумя архивами и `SHA256SUMS`; убедиться, что обычный push тега не создаёт
релиз.

**Acceptance Scenarios**:

1. **Given** тег `v2.0.0` и совпадающая версия в `Cargo.toml`, **When** workflow запускается
   вручную с этим тегом, **Then** создаётся черновик релиза с `freespace-portable-2.0.0-windows-x64.zip`,
   `freespace-portable-2.0.0-linux-x86_64.tar.gz` и `SHA256SUMS.txt`.
2. **Given** тег `v2.0.1`, а версия в `Cargo.toml` — `2.0.0`, **When** workflow запускается,
   **Then** он падает до сборки с сообщением о несовпадении версии.
3. **Given** обычный `git push` тега без ручного запуска, **When** Actions завершаются,
   **Then** новый релиз не появляется.
4. **Given** черновик релиза, **When** сопровождающий публикует его, **Then** артефакты уже
   прикреплены и доступны для скачивания.
5. **Given** один из matrix-джобов упал, **When** workflow завершается, **Then** черновик не
   создаётся или помечается незавершённым; частичный релиз не публикуется автоматически.

### User Story 6 — Прозрачность платформенных возможностей (Priority: P3)

Пользователь и скрипт видят, какие возможности доступны на текущей платформе. GUI скрывает или
деактивирует недоступные действия, CLI возвращает стабильный `E_UNSUPPORTED`, а документация
объясняет причину. Никаких «серых» кнопок, которые падают с невнятной ошибкой.

**Why this priority**: снижает поддержку и предотвращает ложные ожидания при переходе на Linux.

**Independent Test**: на Windows и Linux запросить `capabilities --json` и сравнить с фактическим
поведением GUI/CLI.

**Acceptance Scenarios**:

1. **Given** Linux, **When** пользователь открывает экран инспекции, **Then** вкладки и действия,
   требующие NTFS/ACL/ADS/Restart Manager, скрыты или помечены недоступными.
2. **Given** Linux, **When** скрипт вызывает `freespace shred`, **Then** возвращается
   `E_UNSUPPORTED` и код возврата, документированный для неподдерживаемой возможности.
3. **Given** Windows, **When** пользователь запрашивает capabilities, **Then** доступны MFT, USN,
   Recycle Bin, shred (CLI), ACL, attrs, ADS, unlock и context menu.

### Edge Cases

- XDG-корзина недоступна или не может быть создана на томе (сетевой/съёмный том, нет прав) —
  ошибка без молчаливого permanent.
- Удаление нескольких объектов, часть из которых уже отсутствует, — частичный результат в журнале
  и понятный отчёт.
- Регистрозависимая ФС: `Report.txt` и `report.txt` — разные файлы; проверка конфликтов rename не
  должна склеивать их.
- Путь длиннее `PATH_MAX` на Linux — ошибка до изменения данных.
- Символическая ссылка или точка монтирования внутри выбранного каталога — не обходится без
  явного указания; учитывается согласно выбранному режиму.
- Сканирование каталога без прав — запись помечается как недоступная, итоги не искажаются.
- Старый журнал содержит `quarantine`/`restore` — записи читаются как legacy-аудит, новые не
  создаются.
- Старый `settings.toml` содержит `quarantine_retention_days` — ключ игнорируется, настройки
  загружаются.
- Каталог `data/quarantine` существует от старой версии — приложение его не использует и не
  удаляет автоматически; документация объясняет ручную очистку.
- Приложение запущено из каталога только для чтения — настройки живут в памяти на сессию,
  fallback в системный каталог запрещён.
- Linux-сборка запущена на дистрибутиве без WebKitGTK 4.1 — понятная ошибка запуска.
- Релизный тег отсутствует на remote или указывает на старый коммит — workflow падает до сборки.
- Повторный запуск workflow для того же тега — обновляет черновик, не создаёт дубликат релиза.
- Один matrix-джоб упал — релиз не публикуется автоматически.
- Неподписанный Windows-артефакт вызывает SmartScreen — предупреждение задокументировано.

## Requirements *(mandatory)*

### Функциональные требования

#### Платформы и архитектура

- **FR-001**: Приложение MUST поддерживать Windows 10 21H2+, Windows 11 x64 и Linux x86_64.
- **FR-002**: Все платформенные различия MUST быть изолированы в `freespace-platform` за общим
  набором object-safe трейтов; `freespace-ops`, `freespace-app`, CLI и Tauri MUST NOT содержать
  `cfg(windows)`/`cfg(unix)` в бизнес-логике.
- **FR-003**: Платформа MUST предоставлять машиночитаемый набор `Capabilities` (методы
  сканирования, trash, permanent, shred, ACL, attrs, ADS, unlock, context menu, мониторинг,
  elevation, long paths, регистрозависимость, лимит пути).
- **FR-004**: GUI MUST использовать `Capabilities` для скрытия или деактивации недоступных
  действий; CLI MUST возвращать `E_UNSUPPORTED` с документированным кодом возврата.
- **FR-005**: На Windows MUST сохраняться MFT/USN-сканирование, Recycle Bin, ACL, ADS, атрибуты,
  Restart Manager unlock, context menu и long paths.
- **FR-006**: На Linux MUST использоваться обход дерева каталогов; MFT, USN, ETW и Windows-only
  возможности MUST быть недоступны с явным указанием метода сканирования.
- **FR-007**: Linux MUST перечислять тома через таблицу монтирования и `statvfs`, а занятый размер
  файла MUST учитываться через `st_blocks` с корректной обработкой sparse-файлов.
- **FR-008**: Символические ссылки и точки монтирования MUST NOT обходиться без явного указания
  пользователя.
- **FR-009**: Проверка конфликтов имён MUST учитывать регистрозависимость целевой ФС.
- **FR-010**: Превышение платформенного лимита пути MUST обнаруживаться до изменения данных.

#### Удаление и операции

- **FR-011**: Удаление MUST поддерживать ровно два режима: системная корзина (Recycle Bin на
  Windows, XDG trash на Linux) и permanent.
- **FR-012**: Карантин приложения MUST быть удалён полностью: код, таблица БД, настройки, DTO,
  GUI, CLI, документация и тесты.
- **FR-013**: Любое удаление MUST проходить предпросмотр, явное подтверждение и журналирование.
- **FR-014**: XDG trash MUST следовать freedesktop-спеке; при недоступности корзины приложение
  MUST вернуть ошибку и предложить permanent с отдельным подтверждением.
- **FR-015**: Операции над системными и защищёнными путями MUST требовать дополнительного
  подтверждения; набор защищённых путей MUST быть платформенным.
- **FR-016**: Permanent MUST сопровождаться предупреждением о необратимости.
- **FR-017**: Шредер MUST быть доступен только в Windows CLI; GUI-экран и Tauri-команды MUST быть
  удалены; на других платформах CLI MUST возвращать `E_UNSUPPORTED`.
- **FR-018**: Журнал MUST продолжать отображать старые записи типа `shred`; создание новых
  записей шредера возможно только из Windows CLI.
- **FR-019**: Отмена (undo) MUST поддерживаться для переименования; restore удаления из
  приложения MUST быть удалён, восстановление выполняется средствами системной корзины.

#### GUI и CLI

- **FR-020**: GUI MUST содержать 9 экранов: Обзор, Дерево, Анализ, Дубликаты, Очистка, Журнал,
  Мониторинг, Инспекция, Настройки.
- **FR-021**: Экраны «Шредер» и «Файловые операции» MUST быть удалены из навигации, маршрутизации,
  палитры команд и горячих клавиш.
- **FR-022**: Контекстный rename в дереве MUST сохраниться с предпросмотром и подтверждением.
- **FR-023**: Права, атрибуты и пакетное переименование MUST быть доступны только из CLI.
- **FR-024**: CLI MUST сохранять команды `shred`, `rename`, `acl`, `attrs`; их доступность MUST
  определяться платформой и отражаться в `--help` и `capabilities`.
- **FR-025**: Каждая возможность GUI MUST быть доступна из CLI с JSON-выводом (принцип VI);
  CLI MAY предоставлять больше возможностей, чем GUI.
- **FR-026**: Сохранённые идентификаторы удалённых экранов MUST корректно перенаправляться на
  живые экраны без потери состояния.

#### Поставка и релизы

- **FR-027**: Поставляться MUST только portable-артефакты: Windows ZIP и Linux tar.gz.
  Установщики (NSIS, MSI, deb, rpm, AppImage, Flatpak, Snap) MUST NOT выпускаться.
- **FR-028**: Portable-архивы MUST содержать GUI, CLI, документацию и каталог `data` с описанием
  хранения; Windows-архив MAY содержать опциональный fixed WebView2 runtime.
- **FR-029**: Приложение MUST хранить настройки, журнал, кеш и профиль WebView в `data` рядом с
  исполняемым файлом; системные каталоги MUST NOT использоваться.
- **FR-030**: Linux-архив MUST собираться на Ubuntu 22.04 (baseline glibc) и документировать
  runtime-зависимости WebKitGTK 4.1/GTK3.
- **FR-031**: Релиз MUST запускаться вручную через `workflow_dispatch` с обязательным входным
  тегом; обычный push тега MUST NOT создавать релиз.
- **FR-032**: Workflow MUST проверять, что тег существует и совпадает с версией workspace, до
  начала сборки.
- **FR-033**: Workflow MUST собирать оба артефакта, считать SHA-256 и создавать или обновлять
  черновик GitHub Release; публикация остаётся ручной.
- **FR-034**: Сборки MUST быть неподписанными; отсутствие подписи и предупреждение SmartScreen
  MUST быть задокументированы.
- **FR-035**: Версия MUST иметь один источник истины; CI MUST проверять совпадение версий
  `Cargo.toml`, Tauri-конфигурации, `package.json`/lock и тега.
- **FR-036**: NSIS-конфигурация, `installer/nsis/hooks.nsh` и упоминания установщика в
  документации MUST быть удалены или переписаны под portable-поставку.

#### Совместимость, данные и документация

- **FR-037**: Миграция БД MUST удалить таблицу карантина, сохранив читаемость старых записей
  журнала; каталог `data/quarantine` MUST NOT удаляться автоматически.
- **FR-038**: Ключ `quarantine_retention_days` MUST быть удалён из настроек и CLI; старый
  `settings.toml` с этим ключом MUST загружаться без ошибки.
- **FR-039**: Формат журнала и JSON-контракты MUST оставаться стабильными в пределах мажорной
  версии; удаление карантина оформляется как breaking change версии 2.0.0.
- **FR-040**: Документация MUST быть обновлена на русском (канон) и английском (`docs/en/`):
  платформы, режимы удаления, состав экранов, CLI-команды, portable-поставка, релизный процесс.
- **FR-041**: CHANGELOG MUST содержать раздел `Removed` для карантина, GUI-шредера, GUI-прав и
  экрана «Файловые операции», а также `Changed` для Linux и portable-поставки.
- **FR-042**: Приложение MUST оставаться полностью офлайн; сборка и релиз MUST NOT добавлять
  сетевые вызовы в runtime.
- **FR-043**: Конституция MUST быть обновлена до 2.0.0: принцип I (системная корзина вместо
  карантина), принцип III (раздельные бюджеты Windows/Linux), принцип IV (Windows + Linux),
  принцип VI (GUI — подмножество CLI).

### Key Entities

- **Capabilities**: набор доступных на платформе возможностей и ограничений (методы сканирования,
  trash, shred, ACL, attrs, ADS, unlock, context menu, monitor, elevation, long paths,
  регистрозависимость, лимит пути).
- **Volume**: том или точка монтирования с меткой, ФС, общим/свободным объёмом, методом
  сканирования и доступностью.
- **DeleteRequest**: список объектов, режим (`recycle_bin`/`permanent`), причина, подтверждение.
- **Operation/JournalEntry**: вид, параметры, цели, статус, результат, обратимость и детали;
  записи `quarantine`/`restore` из старых версий — только чтение.
- **PortableArtifact**: имя, платформа, версия, контрольная сумма, состав архива.
- **ReleaseSelection**: тег, версия, черновик/публикация, набор артефактов.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Linux-архив запускается на чистых Ubuntu 22.04/24.04 и Fedora с WebKitGTK 4.1;
  GUI стартует, CLI выполняет `drives`, `scan`, `tree`, `delete` и `--json capabilities`.
- **SC-002**: Windows-архив запускается на чистых Windows 10 21H2 и Windows 11 x64 без установки
  и без записей в реестре.
- **SC-003**: 100% возможностей GUI доступны из CLI с JSON; обратное не требуется.
- **SC-004**: В продукте не остаётся ни одного пользовательского пути создания карантина; поиск
  по коду и строкам интерфейса не находит `quarantine` вне legacy-чтения и миграции.
- **SC-005**: На Linux/macOS `shred` возвращает `E_UNSUPPORTED`; на Windows CLI шредер работает.
- **SC-006**: В GUI ровно 9 экранов; переходы по legacy-идентификаторам не приводят к ошибке.
- **SC-007**: Ручной workflow по тегу создаёт ровно два архива и `SHA256SUMS`; установщиков среди
  артефактов нет.
- **SC-008**: Несовпадение тега и версии останавливает workflow до сборки в 100% случаев.
- **SC-009**: Linux walk-сканирование 1 млн файлов на локальном SSD укладывается в 5 минут;
  отклик UI ≤ 200 мс; память ≤ 4 ГБ на 10 млн узлов.
- **SC-010**: Удаление в XDG trash восстанавливается системными средствами; permanent освобождает
  место; при недоступной корзине ошибка возникает до изменения данных.
- **SC-011**: Миграция БД сохраняет 100% старых записей журнала читаемыми; старый
  `settings.toml` загружается.
- **SC-012**: CI на Windows и Linux зелёный: `cargo fmt --check`, `clippy -D warnings`,
  `cargo test --workspace`; Windows-only тесты корректно пропускаются на Linux.
- **SC-013**: Все версии (workspace, Tauri, npm, тег) совпадают в 100% релизных сборок.
- **SC-014**: Runtime не выполняет сетевых вызовов; телеметрии нет.
- **SC-015**: Документация RU/EN обновлена, `docs/en/` не содержит кириллицы, ID не изменены.

## Assumptions

- 2.0 поддерживает Linux x86_64; ARM, macOS и мобильные платформы — вне области.
- Linux-сборка рассчитана на дистрибутивы с WebKitGTK 4.1 и GTK3; «portable» означает отсутствие
  установки, а не отсутствие системных библиотек.
- XDG-корзина доступна на локальных томах; на сетевых и некоторых съёмных томах удаление в
  корзину может быть недоступно и завершится понятной ошибкой.
- Windows продолжает использовать MFT/USN; Linux использует walk, поэтому бюджет 8 ТБ / 60 с к
  Linux не применяется.
- Пользователи принимают удаление карантина, GUI-шредера и GUI-экрана «Файловые операции» как
  осознанное упрощение мажорной версии.
- Каталог `data/quarantine` от старых версий остаётся на диске и очищается пользователем вручную.
- Релизы публикуются в GitHub Releases вручную; подписи кода нет, сертификат не приобретается.
- Сборка Linux выполняется на Ubuntu 22.04 в CI; Tauri 2 поддерживает целевую конфигурацию.
- Версия 2.0.0 присваивается из-за удаления функций и изменения состава платформ.

## Out of Scope

- macOS, ARM64, мобильные платформы.
- Установщики NSIS/MSI/deb/rpm, AppImage, Flatpak, Snap, portable-режим без `data` рядом с exe.
- Подпись кода и нотаризация.
- Карантин, его restore и срок хранения.
- Шредер в GUI и на не-Windows платформах.
- GUI для прав, атрибутов и пакетного переименования.
- Сетевые функции, облака и телеметрия.
- Автоматическая публикация релиза по каждому тегу.
