# План реализации: Мультитомный снимок

**Branch**: `004-multi-volume-snapshot` | **Date**: 2026-11-20 | **Spec**: [spec.md](./spec.md)

## Summary

Одно сканирование принимает от одного до 32 корней и создаёт **один неизменяемый снимок** с
несколькими корнями. Ядро сканирования переиспользуется как есть: каждый корень по-прежнему
сканируется своим методом (MFT / walk), но узлы добавляются в **одну арену** `FsTree`, поэтому
память не удваивается на слиянии деревьев. Снимок хранит список томов и сессий по корням; дерево
показывает каждый корень отдельной строкой, а аналитика работает по всей арене.

GUI получает множественный выбор томов и явный индикатор состава снимка. CLI получает несколько
позиционных путей для `scan` и `tree`. Запрос сканирования, задача, события прогресса и контракты
обновляются согласованно; версия IPC повышается.

## Technical Context

**Language/Version**: Rust 1.85+ (edition 2024), TypeScript 5.6+, React 19, Node.js 20.19+.

**Primary Dependencies**: без новых зависимостей. Используются существующие `freespace-core`,
`freespace-scan`, `freespace-platform`, `freespace-app`, `freespace-cli`, `tauri` 2, `clap`,
`zustand`.

**Storage**: SQLite-журнал и настройки не меняются. Форматы `.fssnap` и отчётов **не меняются** в
этой фиче: они записывают основной (первый) том и перечисляют все корни. Расширение форматов —
отдельная будущая фича.

**Testing**: `cargo test --workspace`, контрактные тесты `tests/contract/*`, CLI-контракт
`tests/cli_contract.rs`, unit-тесты UI (`vitest`), e2e/a11y — без регрессий.

**Target Platform**: Windows 10 21H2+/11 x64 и Linux x86_64 (portable 2.0).

**Project Type**: Rust workspace + Tauri/React desktop app + CLI.

**Performance Goals**:

- Один том: действующий бюджет 8 ТБ ≤ 60 с на потребительском SSD.
- Два тома суммарно 8 ТБ: ≤ 120 с (последовательное сканирование, без параллельного I/O).
- Память: ≤ 4 ГБ на 10 млн узлов суммарно по всем корням.
- Отклик UI: ≤ 200 мс на корневую страницу дерева.
- Прогресс: не реже 10 событий в секунду, монотонный общий процент.

**Constraints**:

- Один актуальный снимок; новое сканирование объединяет тома с текущим снимком только после
  успеха хотя бы одного корня.
- Сканирование корней последовательное и детерминированное.
- Пересекающиеся и повторяющиеся корни отклоняются до запуска.
- Все системные вызовы остаются в `freespace-platform`; сетевых вызовов и телеметрии нет.
- Разрушающие операции не меняются; журнал получает том цели, а не первый том снимка.

**Scale/Scope**: до 32 корней, до 10 млн узлов, 9 экранов GUI, CLI + GUI, RU/EN.

## 1. Архитектурные решения

### 1.1 Один снимок, много корней

`TreeSnapshot` перестаёт быть «снимком одного тома» и становится «снимком набора корней»:

- `volumes: Vec<Volume>` — уникальные тома в порядке корней;
- `sessions: Vec<ScanSession>` — по одной сессии на успешный корень;
- `volume()` и `session()` сохраняются для совместимости и возвращают первый элемент;
- `volumes()` и `sessions()` — новые аксессоры;
- `volume_for_path(&Path)` — том, которому принадлежит путь (самый длинный подходящий mount
  point), для журнала и метаданных задач.

Конструктор `TreeSnapshot::new` остаётся для одиночного тома; добавляется
`TreeSnapshot::new_multi`.

### 1.2 Сканирование в общую арену

В `freespace-scan`:

- `scan()` разделяется на `scan_into(request, tree, observer) -> RootScanOutcome` и финальную
  агрегацию.
- `scan_into` сканирует один корень, добавляет его как новый корень арены, считает узлы только
  этого корня и **не** вызывает `recompute_totals`, `compact` и `validate`.
- `scan_many(requests, observer) -> ScanManyResult` создаёт одну `FsTree`, последовательно
  вызывает `scan_into`, изолирует ошибки корней, останавливается при отмене и один раз выполняет
  `recompute_totals`, `validate`, `compact`.
- Обёртка наблюдателя пересчитывает локальную долю корня в общий процент
  `(index + local_fraction) / roots_count` и передаёт события наружу. После последнего корня
  отправляется финальное событие `Finished` с долей 1.0.
- Если все корни завершились ошибкой, возвращается первая ошибка; если хотя бы один успешен —
  результат с `failures`.

### 1.3 Запрос и задача

- DTO `ScanRequest` получает `paths: Vec<String>` вместо `path`.
- `Task` получает `volume_ids: Vec<String>`; `volume_id` остаётся первым элементом для
  совместимости.
- `ScanSummary` события получает `volumes: Vec<String>` и `methods: Vec<String>`; `method`
  содержит единственный метод или `mixed`.
- `ScanSessionSummary` остаётся по одной записи на корень; `scan_sessions` возвращает их все.

### 1.4 Валидация

- 1..=32 путей, каждый абсолютный и непустой.
- Повторяющиеся корни отклоняются по платформенному ключу пути.
- Пересекающиеся корни отклоняются после канонизации: ни один корень не является предком другого.
- Проверка выполняется до резервирования томов и запуска воркера.

### 1.5 Резервирование томов

- `AppState` получает `reserve_scans(task_id, volume_ids, cancel)` и `release_scans(volume_ids)`.
- Если хотя бы один том занят, задача не запускается (`E_BUSY`), частичного резервирования нет.
- Задача хранит `volume_ids`; после завершения все брони снимаются.

### 1.6 Прогресс, отмена и ошибки

- Прогресс последовательный: `том i из N`, общий процент монотонный.
- Отмена между корнями не запускает оставшиеся; уже собранные данные сохраняются.
- Ошибка корня добавляет предупреждение `корень: причина`; задача становится `partial`.
- Если успешных корней нет, снимок не устанавливается, задача становится `failed`.

### 1.7 GUI

- `snapshotStore` хранит `volumes: VolumeSummary[]` и производный `volume` (первый) для
  совместимости.
- После `scan-completed` фронтенд запрашивает `snapshot_volumes(generation)`.
- Обзор: том выбирается нажатием на карточку, кнопка «Анализировать» запускает выбранный набор.
  Карточка показывает признак сканирования, если её том входит в `task.volume_ids`.
- Дерево: суммарный размер равен сумме размеров всех корневых строк; контекст называет число
  томов; при одном томе тексты не меняются.
- Остальные экраны используют первый том только там, где нужен путь по умолчанию; данные берутся
  из всего снимка.

### 1.8 CLI

- `freespace scan <PATH>...` и `freespace tree <PATH>...` принимают один или несколько путей.
- `scan` вызывает то же `scan_many`; JSON содержит `volumes`, `roots`, `methods`, `total`,
  `issues`, `node_count`; `--snapshot-out` пишет основной том и все корни.
- Один путь даёт прежний формат с добавлением массивов (обратная совместимость по полям).

## 3. Производительность и память

- Одна арена на весь снимок; корни добавляются последовательно, промежуточные деревья не
  создаются.
- Пиковая память = итоговая арена + временные структуры одного корня (MFT-записи, карты), как и
  сегодня для одного тома.
- `recompute_totals`, `validate` и `compact` выполняются один раз после последнего корня.
- Прогресс взвешивается по числу корней, а не по байтам: это дёшево и монотонно; текущий том и
  путь показываются явно.
- UI не загружает все корни сразу: `tree_root` возвращает страницу корней, как и раньше.

## 4. Совместимость и миграции

- Версия IPC повышается; контрактные фикстуры и тесты обновляются.
- `volumes_current` сохраняется и возвращает первый том; новый `snapshot_volumes` возвращает все.
- Старые клиенты с `path` не поддерживаются после повышения версии IPC; это внутренний протокол
  приложения.
- `.fssnap` и отчёты остаются версии 1: основной том + все корни. Это ограничение зафиксировано в
  spec и quickstart.
- Настройки и журнал не мигрируют.

## 5. Риски

| Риск | Снижение |
|---|---|
| Двойной учёт при пересекающихся корнях | Валидация до запуска + тест на `C:\` и `C:\Users`. |
| Рост памяти на многотомном снимке | Одна арена, последовательные корни, один `compact`. |
| Немонотонный прогресс | Формула `(index + local) / N`, тест на монотонность. |
| Потеря результата при ошибке одного тома | Изоляция ошибок, `partial`, снимок устанавливается при ≥1 успешном корне. |
| Расхождение GUI и CLI | Общее ядро `scan_many`, контрактные тесты CLI и IPC. |
| Некорректный том в журнале | `volume_for_path` и тест операции на втором томе. |
