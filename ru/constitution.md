# FreeSpace Constitution

## Core Principles

### I. Безопасность разрушающих операций (NON-NEGOTIABLE)

Любая операция, изменяющая или удаляющая данные пользователя (удаление, перезапись,
переименование, перемещение, смена прав и атрибутов), MUST выполняться только после
явного подтверждения пользователя с предпросмотром списка затронутых объектов и их
суммарного объёма. По умолчанию удаление MUST направлять объекты в Корзину или карантин;
безвозвратное уничтожение (шредер) MUST быть отдельным осознанным действием с
дополнительным предупреждением. Пакетные операции MUST поддерживать отмену (undo) там,
где она технически возможна, и MUST журналироваться. Операции над системными и
защищёнными каталогами MUST требовать прав администратора и дополнительного
подтверждения. Приложение MUST NOT изменять данные за пределами явно выбранной
пользователем области.

Обоснование: утилита работает с единственными копиями пользовательских данных; ошибка
необратима, поэтому безопасность важнее удобства и скорости.

### II. Точность учёта дискового пространства

Приложение MUST различать логический размер файла и размер, фактически занимаемый на
диске. Hard links MUST учитываться один раз на физический файл; junction-точки и symlinks
MUST NOT обходиться без явного указания пользователя; сжатые NTFS-файлы, sparse-файлы и
alternate data streams (ADS) MUST учитываться в расчётах согласно фактическому расходу
места. Итоговые размеры каталогов MUST быть согласованы с данными файловой системы и MUST
NOT завышать или занижать занятое пространство. Отчёты MUST явно указывать, какой тип
размера показан (логический или на диске).

Обоснование: главная ценность продукта — достоверный ответ на вопрос «куда ушло место»;
неточный учёт обесценивает все остальные функции.

### III. Производительность на больших объёмах

Сканирование NTFS-тома MUST использовать прямое чтение MFT как основной путь и MUST
выполнять анализ тома объёмом до 8 ТБ не дольше 60 секунд на типичном потребительском SSD
(целевой показатель). Пользовательский интерфейс MUST оставаться отзывчивым во время
сканирования и любых длительных операций: работа MUST выполняться в фоновых потоках,
списки и деревья MUST быть виртуализированы, результаты MUST отображаться постепенно.
Повторные сканирования MUST поддерживать инкрементальное обновление через USN-журнал.
Любая длительная операция MUST иметь измеримый бюджет времени и памяти, зафиксированный
в плане.

Обоснование: на дисках в единицы и десятки терабайт медленное сканирование делает
инструмент непригодным, а зависший UI воспринимается как сбой.

### IV. Нативная точность Windows

Приложение MUST быть нативным для Windows 10 (21H2+) и Windows 11 x64 и MUST полностью
поддерживать NTFS: длинные пути (свыше 260 символов) без необходимости включать системную
политику, Unicode-имена, права и владельцев NTFS, атрибуты файлов, UAC-elevation по
требованию. Для томов, отличных от NTFS (FAT32, exFAT, ReFS), MUST существовать корректный
fallback на обход дерева каталогов с явным указанием применённого метода сканирования.
UI-фреймворк MUST NOT ограничивать доступность системных возможностей ядра. Все системные
вызовы MUST быть изолированы в отдельном слое платформы.

Обоснование: продукт решает задачи, недоступные обычному Проводнику; любая потеря нативной
функциональности разрушает его ценностное предложение.

### V. Тест-первый подход к операциям с файловой системой (NON-NEGOTIABLE)

Критические модули (сканирование, хеширование, шредер, удаление и перемещение, работа с
правами, длинными путями, ссылками) MUST покрываться автоматическими тестами до слияния
изменений. Тесты MUST использовать изолированные фикстуры файловой системы (временные
каталоги, тестовые VHD-образы) и MUST NOT затрагивать реальные пользовательские данные.
Результаты сканирования и отчёты MUST быть детерминированными: одинаковый вход MUST давать
одинаковый выход. Для новых возможностей MUST действовать цикл «тест → падение →
реализация».

Обоснование: ошибки в работе с ФС приводят к потере данных и ложным отчётам; тесты —
единственная защита, воспроизводимая в CI.

### VI. Паритет CLI и GUI

Каждая пользовательская возможность, доступная в графическом интерфейсе, MUST быть
доступна через командную строку с машиночитаемым выводом (JSON) и MUST поддерживать
неинтерактивный режим для Планировщика заданий Windows и CI. Форматы отчётов и коды
возврата MUST быть документированы и стабильны в пределах мажорной версии. GUI и CLI MUST
использовать одно и то же ядро.

Обоснование: автоматизация — ключевой сценарий для системных администраторов; расхождение
поведения GUI и CLI порождает невоспроизводимые результаты.

### VII. Приватность и работа офлайн

Приложение MUST полностью работать без сетевого подключения. Сканируемые данные,
метаданные, отчёты и снимки MUST NOT покидать машину пользователя. Телеметрия MUST
отсутствовать по умолчанию; любая будущая отправка диагностики MUST быть явно включаемой
и документированной.

Обоснование: утилита видит содержимое всего диска, включая конфиденциальные данные;
доверие пользователя критично.

## Технологические и платформенные ограничения

- Язык реализации — Rust (stable, edition 2024); UI — egui/eframe как основной вариант;
  Tauri допускается только при обоснованной необходимости веб-технологий и не должен
  снижать нативную функциональность.
- Целевые платформы v1: Windows 10 21H2+ и Windows 11, x64. Кроссплатформенность не
  является целью v1.
- Основная файловая система — NTFS; прочие ФС поддерживаются в режиме fallback.
- Конфигурация и пользовательские данные хранятся локально; формат снимков (snapshots)
  версионируется.
- Документация проекта ведётся на двух языках: русском (`ru/`) и английском (`en/`);
  канонические артефакты Spec Kit пишутся на русском и зеркалируются в оба каталога.

## Процесс разработки и контроль качества

- Разработка ведётся по процессу Spec-Driven Development Spec Kit: конституция →
  specify → clarify → plan → checklist → tasks → implement → converge; артефакты хранятся
  в `specs/<feature>/`.
- Каждый план MUST содержать раздел Constitution Check и подтверждать соответствие
  принципам; отклонения MUST обосновываться в Complexity Tracking.
- Изменения кода MUST проходить `cargo fmt --check` и `cargo clippy -- -D warnings`;
  сборка MUST воспроизводиться на CI.
- Коммиты MUST следовать Conventional Commits; изменения поведения MUST отражаться в
  CHANGELOG.
- Проверка на реальных дисках MUST выполняться вручную по quickstart-сценариям перед
  релизом.

## Governance

Конституция преобладает над остальными практиками проекта. Поправки MUST оформляться
отдельным изменением с обоснованием, обновлением версии и даты, а также Sync Impact
Report. Версионирование конституции — семантическое: MAJOR — удаление или переопределение
принципов, MINOR — добавление принципа или существенное расширение, PATCH — уточнения
формулировок. Каждый план и ревью MUST проверять соответствие конституции; несоблюдение
MUST блокировать слияние до устранения или явного обоснования. Ответственность за
соблюдение несут автор изменения и ревьюер.
